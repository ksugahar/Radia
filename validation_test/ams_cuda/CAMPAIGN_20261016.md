# Same-host AMS and fixed IC campaign (2026-10-16)

The independently authored checked unit-cube HCurl cases use unit reluctivity,
positive unit gauge mass, unit x-directed current density and homogeneous
tangential boundary conditions. All quantities use SI. CPU NGSolve runs at
1 and 16 threads, BLAS at 1. All solves start from zero. The p=1 study has a
separate initialized call and two balanced forward/reverse cycles; repeated
RHS scales retain the matrix and preconditioner. Setup and gathered solve
times include host/device transfers.

This is candidate evidence: unchanged 0.1.5rc1 base wheel plus the explicit
fixed IC overlay. It is not formal-wheel acceptance. The production IC MEX
SHA256 is `dc1a4a3ea7fd7b68d3ea437216a96fed219ca660d7d71c812adb3b7491677be8`,
identical to the RTX 5000 validation artifact. Actual loaded-module hashes
were checked. The test-only mismatch MEX is separately identified and is
also byte-identical across the two GPUs.

360 p=1 and 24 high-order solve checks passed independent Python NGSolve
`sparsecholesky` solution and original free-DOF residual gates. Maximum
solution error is 1.122e-11; maximum true relative residual is 5.621e-12.
Native checks use the projected original operator (constrained diagonals = 1,
constrained RHS = 0). Both normal and selected-device mismatch lifecycle
checks passed; physical multi-GPU switching is not tested.

GPU speedup is case-dependent. At 106,272 DoFs both GPU reused routes beat
their CPU16 counterparts, while fresh GPU construction is slower. CPU1 IC
is faster than both CPU16 and GPU IC at the smallest size.

At the largest size, measured GPU host-basis setup is 1.394 s for AMS and
1.392 s for IC. Relative to fresh totals, this gives a phase share of about
74% and 43%, respectively, making host setup a concrete fresh-solve target.
This setup cost is absent from reused solves. IC retained native buffers
are 80,927,700 bytes; the setup owned-buffer bound is 93,768,036 bytes,
including the owned 4 MiB cuBLAS workspace. These exclude opaque runtime
allocations and caller inputs/outputs, and do not certify a whole-device peak.

## p=2/3 solver-only feasibility on the same geometry

CPU BDDC uses the registered `sparsesolv_ams` coarse solver, explicit
`sparsecholesky` local inversion, static condensation and full-solution
recovery. Independent original-system checks verify that recovery. The GPU
IC receives an explicitly projected CSR validation fixture; its action is
checked against NGSolve before transfer. This exchange is a validation route,
not a required GPU-user assembly adapter. High-order GPU FE assembly remains
unsupported by `assembleHCurl`.

| Order / total DoFs | CPU1 BDDC+AMS reuse (s) | CPU16 BDDC+AMS reuse (s) | GPU IC reuse (s) | BDDC+AMS / IC iterations |
| --- | ---: | ---: | ---: | ---: |
| 2 / 43,114 | 0.1911 | 0.0515 | 0.3123 | 47 / 258 |
| 3 / 115,141 | 0.7838 | 0.1435 | 0.8668 | 68 / 282 |

All routes passed; GPU IC is about six times slower than CPU16 BDDC+AMS
on these reused solves. These are feasibility measurements from one
construction and four zero-start RHS solves, not broad high-order performance
certification. The iteration gap supports investigating a stronger GPU
preconditioner before claiming high-order acceleration.
