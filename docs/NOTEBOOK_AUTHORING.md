# Write an application notebook readers can inspect and reproduce

The executed notebook introduces a feature and explains its demonstrated result.
Operational workflows use MCP or human–AI collaboration through Cubit and
Simulink. Executable usage samples belong in [tests/](../tests/README.md);
physics and application samples belong in [validation_test/](../validation_test/README.md).
Link relevant cases and operating interfaces rather than making a notebook
the required workbench. Preserve saved code and output so readers can inspect
and, where supported, reproduce the demonstration.

Keep the
[application gallery](APPLICATION_GUIDE.md) short and link to that notebook;
avoid maintaining a second table of the same numerical results in an overview page.

## Lead with the engineering decision

Before the first code cell, include:

1. **Question:** what will the reader decide from the calculation?
2. **Model and conditions:** geometry, units, material law, excitation and boundaries.
3. **Result preview:** a saved figure or scene with a caption explaining what to inspect.
4. **Interpretation:** the measured quantity and the supported conclusion.
5. **Read or rerun:** dependencies, working directory, inputs to change and what execution does.
6. **Use this capability:** the supported MCP or Cubit/Simulink route and relevant
   test or validation case. State gaps explicitly; a saved notebook alone does
   not prove an end-to-end MCP workflow.

Follow with formulation, code, saved results, validation and limitations. Describe
technical details where they explain a design choice or a reproducibility condition.
See the [coil](stream_function/theory.ipynb),
[motor](electric_machine/angle_periodic_motor_rom.ipynb) and
[thermal](induction_heating/axisymmetric_p2_thermal.ipynb) introductions.

## Keep the figure attached to its calculation

Use the actual case geometry and saved field scene where available. Quantitative
curves supplement those views. Label analytical reference plots, geometry
schematics and figures from separate runs explicitly. A related illustration
must not imply it was generated by the displayed calculation.

Captions identify the physical quantity, units, operating condition and the
comparison. For 3D geometry or fields, retain the saved interactive geometry
and principal-field views required by the repository notebook policy. Do not
create a decorative rendering as a substitute for missing numerical evidence.

## State what Run All does

Selected application introductions are result readers: numerical drivers and
checked records live in `validation_test/`; notebooks load the records and
draw figures. Show the numerical execution date, runtime, conditions and check
scope. A reader must fail on missing or rejected data rather than silently
falling back to an older record or starting a solver. Keep the wider numerical
study out of the introductory page.

Distinguish a notebook that recomputes a field solution from one that loads a
record and redraws a figure. If it does both, identify the stages. Name expensive
steps and the appropriate execution environment. Reading a saved native result
is not a fresh native run; changing a plot is not a new numerical validation.

## Review before linking from the gallery

- Provide a working route to the owning MCP or Cubit/Simulink interface and to
  relevant `tests/` or `validation_test/` cases. Describe whether each linked
  case checks source structure, synthetic inputs or a real numerical solve.
- Explain when a linked sample uses a different geometry from the illustration.
  Keep pass counts and accuracy claims tied to an identifiable result record.
- Match prose numbers and target names to saved outputs. Identify different runs
  or different metrics before placing them in a comparison table.
- Keep code, saved outputs and execution counts intact during editorial changes.
  If calculation code changes, rerun and validate on the permitted compute host.
- Check notebook schema, local links, figures and a read-only HTML export.
  An export check establishes rendering, not numerical validity.
- Keep canonical bibliography generation and publication boundaries unchanged.
- Record unresolved issues instead of presenting them as passed checks.

The site can show explanation and outputs before code, while the downloadable
notebook retains the full calculation. Code folding depends on the selected
site renderer; notebook metadata alone is not a promise of that behavior.
